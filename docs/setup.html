Setup checklist

The commands, in order, with nothing in between. For what each step does, why, and how to tell it worked, open architecture.html and read sections 13 to 17.

1First time, local

In order. Each step needs the one before it — the settings file has to exist before anything can be written into it.

1 · The code

Terminal
node -v            # needs v20.9 or newer
npm install
npm test           # 510 passing means the code is sound

2 · The Supabase project

New project, named preppy-dev, nearest region. Set a database password and keep it — it cannot be recovered, and step 3 needs it.

3 · The settings file

It does not exist yet. Copy the example, then fill it in — everything after this writes into it.

Terminal
cp -n .env.example .env.local   # -n so it cannot overwrite a filled-in one

Four values, from two places in the dashboard. CRON_SECRET stays blank until you deploy.

Line in .env.localWhere
NEXT_PUBLIC_SUPABASE_URLSettings → API Keys
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
or NEXT_PUBLIC_SUPABASE_ANON_KEY
SUPABASE_SECRET_KEY
or SUPABASE_SERVICE_ROLE_KEY
DATABASE_URLConnect button at the top → Session pooler
CRON_SECRETleave blank; production only

Two generations of key, both valid

Settings → API Keys shows current keys (sb_publishable_..., sb_secret_...) and the legacy pair it is replacing (long JWTs starting eyJ, labelled anon and service_role). Prefer the current ones. The app takes either name for either slot, so fill in whichever pair you have.

.env.local carries the current names as live lines with the legacy names commented out beneath them. If yours are the legacy ones, swap which of the two is commented.

cp -n, not cp

Plain cp overwrites. Run it over a filled-in .env.local and your keys are gone, with no copy anywhere — the file is git-ignored by design.

Session pooler, specifically

The Connect panel offers three and only one is right here. The direct connection is IPv6-only without the paid add-on, so on a normal IPv4 network it cannot be reached at all. The transaction pooler on 6543 has no prepared statements, which npm run migrate uses. The session pooler is IPv4 on every plan and supports everything a migration needs.

You can tell it by the username, which carries the project ref: postgres.[REF]@aws-0-[region].pooler.supabase.com:5432. URL-encode any @ : / or # in the password.

Check it:

Terminal
npx tsx --env-file=.env.local scripts/preflight.ts local
  preflight (local): environment looks right.

No DATABASE_URL? npm run migrate -- --print prints the SQL to paste into SQL Editor → New query instead, one file at a time, in order. Either way you should end with twelve tables plus schema_migrations, and on a current Supabase project all thirteen show an RLS enabled badge — their own event trigger turns it on for anything created in public. An older project may leave the ledger without one, which is equally fine.

Why it may say the baseline is pending

On a database that was set up by hand before any of this existed, nothing was recorded, so --status reports even 0001_baseline.sql as pending. Expected. Run npm run migrate anyway — every file is written to be safe to run twice, so the baseline passes straight through and gets recorded, and only the later files change anything. After that one run the list is accurate for good.

5 · Email confirmation off

Authentication → Sign In / Providers → Email → turn Confirm email off.

This one is not optional

Skip it and every login is refused as unconfirmed — but the form only says "wrong username or password", so it looks like the password is wrong when it is not.

6 · Accounts, and run it

Terminal
npm run seed          # prints passwords ONCE - copy them
npm run dev           # http://localhost:3000

The secret key

It bypasses every access rule in the database. It belongs only in .env.local, which git already ignores. Never paste it anywhere else.

2Every day

Terminal
npm run dev

After pulling new code: run npm run migrate. If nothing is pending it says so and stops; if a new file has appeared it applies it. Skipping it is what produces errors like column ... does not exist.

Restart it after editing .env.local — environment changes are not picked up while it runs. This is the most common thing to trip on.

3Publishing a paper

Terminal
npm run check -- my-paper.json          # validate before opening the app
npm run check -- my-paper.json --images ./img

Then in the app: Admin → Upload a paper → read the preview → Schedule. The upload screen has an optional name box: blank uses the name in the file, and anything typed wins. A paper can also be renamed later from Manage. You choose its date and times on the schedule form; Admin → Default times only sets what is offered by default, and Admin → Paper pattern what a section holds when the file does not say. More than one paper can run in a day, and they may share a window — a student sits one at a time and chooses the order. Two papers on one night need different names. Copy format/sample.json as your starting point. The format is specified in architecture.html section 7.

If it goes wrong while it is running

Manage, on a scheduled paper, is the screen for it. Nothing here needs the terminal.

What happenedWhat to press
One key is wrongNothing on Manage. Correct it on the paper itself, question by question — every attempt is scored again on the spot, and only the students whose result moved are told
The marking is wrongWhat the questions are worth. Saves, then scores every finished attempt again
Somebody needs longer to startThe window. Moving the last moment to start moves the finish with it, so they still get the whole paper
The paper is broken and must stop nowEnd it now. Everyone still in it is submitted and scored where they stand, and answers open at once. It cannot be undone
The file was wrong, and nobody has sat itUpload a corrected file. Same paper, same window, new questions
The file was wrong, and somebody hasEnd it, then Delete this paper — which takes their attempts with it, and says how many — then upload the corrected one as a new paper

Preparing people for a second exam

Skip this if everybody here is sitting the same exam. With one exam nothing in the console mentions this at all, which is the intended state.

StepWhere
Add the examAdmin → Exams. A name, and an address derived from it. It starts on the shipped pattern: four sections, 55 questions, 45 minutes
Give it its real shapeAdmin → Pattern, with the new exam chosen at the top. Add or remove sections, move them, rename them — Professional Knowledge is where the discipline goes. Do this before uploading anything, since a paper is checked against the pattern of the exam it is for
Put people on itAdmin → People. An Exam column appears once there is more than one; change anybody's from the row. New accounts get a picker
Upload a paper for itAdmin → Upload a paper, and choose the exam at the top. Two exams may run a paper at the same time on the same day

Closing an exam stops new papers being scheduled on it and changes nothing else: its papers, attempts and leaderboard stay. The last open one cannot be closed.

4Shipping a change

Terminal
npm run build:prod      # preflight + typecheck + 510 tests + build
git add -A && git commit -m "what changed"
git push                 # Vercel deploys by itself

Never deploy inside a paper's window

Somebody is probably mid-attempt. Each paper carries its own times now, so check the admin home — it lists today's papers with their windows — and ship outside all of them.

5First time, production

A second Supabase project, and a Vercel deployment that points at it. Nothing here reuses the development project, and your laptop's .env.local is never changed — the whole reason for two projects is that a mistake made while building cannot touch a night's real attempts.

Every step is written out here. Nothing says "as in section 1": you can work through this page without scrolling back. About forty minutes, most of it waiting. Do it in daylight, well before a paper night.

What you need before you start

A Supabase account, a GitHub account, and a Vercel account (sign in to Vercel with GitHub and the two are already connected). The code on your machine, with npm install already run. All three services are free at this size.

1 · Create the production Supabase project

  1. In the Supabase dashboard, New project.
  2. Name it something you cannot mistake for the other one. preppy-prod.
  3. Choose the region closest to your students. For an Indian cohort that is ap-south-1, Mumbai. This is the one setting you cannot change later without rebuilding the project.
  4. Set a database password and save it somewhere you will still have in six months. It is shown once and cannot be recovered, it is not your Supabase account password, and step 3 needs it.
  5. Create, then wait. Provisioning takes a minute or two and nothing works until it finishes.

2 · Turn email confirmation off

Authentication → Sign In / Providers → Email, and turn Confirm email off.

Do this before step 6, not after

Preppy has no email addresses. A username becomes name@preppy.local, a synthetic address that exists only to satisfy Supabase and receives nothing. With confirmation on, every account the seed creates waits for a confirmation mail that will never arrive and can never be confirmed, and nobody can log in. Fixing it afterwards means deleting the accounts and seeding again.

3 · Collect the five values

All from preppy-prod. A key from the development project does not work here — they are different projects with different keys.

ValueWhere in the dashboardWhat it looks like
NEXT_PUBLIC_SUPABASE_URL Connect at the top, or Settings → API Keys https://ref.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY Settings → API Keys, the publishable key sb_publishable_…
SUPABASE_SECRET_KEY Settings → API Keys, create a secret key sb_secret_…
DATABASE_URL Connect at the top → Session pooler postgresql://postgres.ref:password@aws-0-region.pooler.supabase.com:5432/postgres
CRON_SECRET Not from Supabase. Generate it: npm run secret 48 hex characters; 16 is the minimum accepted

Two generations of key, both valid

Settings → API Keys shows the current keys (sb_publishable_… and sb_secret_…) and the legacy pair they replace: long JWTs beginning eyJ, labelled anon and service_role. Prefer the current ones; Supabase is retiring the others.

The app accepts either generation under either name, so use whichever your project shows. If yours are the legacy pair, the variables are NEXT_PUBLIC_SUPABASE_ANON_KEY and SUPABASE_SERVICE_ROLE_KEY. Set one name per slot; setting both is harmless but pointless.

The publishable key and the secret key are not interchangeable

Anything in a NEXT_PUBLIC_ variable is compiled into the JavaScript a browser downloads. A secret key there is published to everyone who loads the page, and it bypasses every access rule in the database.

The build checks twice — preflight refuses to start if it sees a secret key in the public slot, and the bundle scan reads the compiled output afterwards — but if such a key has ever been in a build or a commit, rotate it in the dashboard rather than reasoning about who might have seen it.

Session pooler, specifically

The Connect panel offers three connection strings and only one works here. The direct connection is IPv6-only unless you pay for the IPv4 add-on, so on a normal network it cannot be reached at all. The transaction pooler on port 6543 has no prepared statements, which the migration runner uses. The session pooler on port 5432 is IPv4 on every plan and supports everything a migration needs.

You can tell it apart by the username, which carries the project ref: postgres.ref@aws-0-region.pooler.supabase.com:5432. The password in it is the database password from step 1, and any @ : / # in that password must be URL-encoded or the address will not parse.

4 · Write a throwaway settings file

The migration runner and the seed script talk to whichever database their environment points at. Rather than editing .env.local and risking forgetting to change it back, put the production values in a separate file, use it for two commands, and delete it.

.env.prod.local
# PRODUCTION. Delete this file when step 6 is done.
NEXT_PUBLIC_SUPABASE_URL=https://your-prod-ref.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_…
SUPABASE_SECRET_KEY=sb_secret_…
DATABASE_URL=postgresql://postgres.ref:password@aws-0-region.pooler.supabase.com:5432/postgres

Check it before using it. This reads the file and says what is wrong, if anything, without touching the database:

Terminal
npx tsx --env-file=.env.prod.local scripts/preflight.ts local
  preflight (local): environment looks right.

local rather than prod is deliberate here: the prod check also requires CRON_SECRET, which belongs to Vercel rather than to this file.

Do not point .env.local at production, even for a minute

npm run dev, npm run migrate and npm run seed all read .env.local without being told to. One forgotten line and a development command is operating on real attempts. The separate file costs nothing and removes the possibility.

.env* is gitignored, so neither file can be committed by accident — but a file on your disk is still a file on your disk, which is why step 6 deletes it.

7 · Put the code on GitHub

Vercel deploys from a git repository. If the code is not there yet, create an empty private repository on GitHub and push to it:

Terminal

  (no .env file may appear in this list)

.env* is gitignored, so your keys do not travel with the code. That first command is worth running every time regardless.

8 · Import into Vercel

  1. At vercel.com, Add New → Project, and pick the repository. Next.js is detected; leave the build and output settings alone.
  2. Check Settings → Node.js Version is 20.9 or newer. Next 16 says so in its own engines field, and a project pinned to 18.x fails during install with an error about the engine rather than about anything you wrote.
  3. Check Settings → Functions → Function Regions says Mumbai (bom1), or whichever region your Supabase project is in. vercel.json already asks for bom1, so this is a confirmation rather than a step — but it is the single setting with the largest effect on how fast the site feels, and the note below says why.
  4. Open Environment Variables and add four, all from preppy-prod:
    NameValue
    NEXT_PUBLIC_SUPABASE_URLfrom step 3
    NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
    or NEXT_PUBLIC_SUPABASE_ANON_KEY for a legacy key    		from step 3
    SUPABASE_SECRET_KEY
    or SUPABASE_SERVICE_ROLE_KEY for a legacy key    		from step 3
    CRON_SECRETnpm run secret, if you have not already
    Apply each to Production. Add them to Preview too if you want preview deployments to work; leave Development alone, since that is your laptop and it reads .env.local.
  5. Deploy.

Run the functions where the database is, or the site is slow for no visible reason

Vercel Functions default to iad1, Washington DC, for every new project — sensible, since most databases are on the US east coast. This one is not: a Supabase project created in ap-south-1 is in Mumbai.

Left on the default, every query crosses the Atlantic and most of Asia and comes back. A dashboard render makes several Supabase calls one after another, and each of them pays that round trip, so a page that takes a fraction of a second on a laptop in India takes a second or two deployed. Nothing errors and nothing in the logs looks wrong; it is simply slow, and the cause is a map rather than the code.

vercel.json carries "regions": ["bom1"], which is Vercel's Mumbai region — the same city as the database. If your Supabase project is somewhere else, change it to match: the region list is at vercel.com/docs/regions, and Vercel's own advice is that "functions should be executed in the same region as your database, or as close to it as possible".

Four variables, and DATABASE_URL is not one of them

The application never opens a Postgres connection — it speaks to Supabase over HTTPS. The only thing in this repository that reads DATABASE_URL is the migration runner, which runs from your machine. Putting it in Vercel stores a production database password somewhere that has no use for one.

9 · What the deploy does, and how to read a failure

Vercel runs npm run build, which is build:prod:

StepWhat it catches
preflight prodA missing or malformed variable, before anything expensive runs. It names the variable and what it expected, including a secret key in the publishable slot or a value pasted with a trailing space
typechecktsc --noEmit over the whole repository, tests included
testAll 510. They need no database, so they run on Vercel exactly as they do on your machine. One failure fails the deploy and the live site does not change
next buildThe build itself, with browser source maps dropped
check-bundleReads everything under .next/static — the files a browser downloads — and fails if any of it contains the secret key's name, the sb_secret_ prefix, or the key itself

A good build ends with a line like check-bundle: 37 client files scanned, no secret key found. Worth looking for the first time. If the build fails, read the first ten lines of the log: preflight runs before everything and names what it is unhappy about.

10 · Check the nightly sweep registered

Settings → Cron Jobs should list two entries for /api/cron/finalise: 30 7 * * * and 30 19 * * *. That is 07:30 and 19:30 UTC, which is 1 PM and 1 AM IST. They come from vercel.json in the repository, so you do not create them by hand — if they are missing, that file did not reach the deploy.

Vercel presents CRON_SECRET as a bearer token and the endpoint refuses anything else, so no one else can trigger a scoring run. With the variable unset the endpoint answers 500 and logs why, rather than quietly doing nothing: an unfinalised attempt is a student without a score.

Afterwards: shipping a change

Terminal
npm run build:prod      # the same five steps, on your machine first
git add -A && git commit -m "what changed"

If the change includes a new migration, apply it to production the same way as step 5 — write .env.prod.local again, run the runner against it, delete the file. Deploy code that expects a column the production database does not have yet and the site breaks for everyone at once.

Every script in package.json, grouped by when you reach for it. The -- before a flag is npm's, not the script's: it means "pass the rest through".

Two useful things that are not npm scripts

Preflight on its own, which is the quickest way to find out whether .env.local is right. It names the variable and the dashboard page for anything missing or wrong:

Terminal
npx tsx --env-file=.env.local scripts/preflight.ts local

And the bundle scan, which normally runs as the last step of a build, against a build you already have: npx tsx scripts/check-bundle.ts. It needs something to look at and says so if there is nothing.

7Quick fixes

SymptomFix
"Not configured yet".env.local incomplete, or the server needs restarting
Login rejects a password you know is rightEmail confirmation is still on. Then npm run seed -- --reset
"Cannot build for production"Working as intended — it names the missing variable
Seeding errorsTables missing. Run npm run migrate
The sweep did not runAdmin home → Finalise open attempts now
A paper will not deleteSomebody has a counted attempt on it. A trigger is refusing
Leaderboard missing a paperA paper joins the board when the first student finishes it, or at its close if nobody did. A paper nobody has sat and that has not closed is on nobody’s board yet. With more than one exam, check you are looking at the right board
A student sees no papers at allAdmin → People: their Exam is unset, or set to one with nothing scheduled
An upload is refused for its sectionsIt is being checked against the wrong exam. Pick the right one at the top of the upload screen

Three questions answer most problems:

  1. Which database am I talking to? Compare the URL in .env.local with the project name in Supabase.
  2. Did the schema apply? Table Editor: twelve tables plus schema_migrations, essentially all of them showing an RLS badge.
  3. Does it fail without a database? npm test. If those pass, it is configuration, not logic.
