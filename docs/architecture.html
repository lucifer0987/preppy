Part I

How it works

The mental model. Read this once and the code stops being surprising.

1The shape of it

Preppy is one Next.js application talking to one Supabase project. There is no separate backend service, no queue, no cache layer, and no second database. Everything is TypeScript.

That is a deliberate size. The system serves six accounts. Every extra moving part would be something that can break mid-paper while five people wait, in exchange for capacity nobody needs.

What each piece does

Supabase StorageDiagrams for DI sets and puzzlesPrivate bucket; served through an app route that checks permission

Why no separate backend

A Next.js server action is a backend endpoint: it runs on the server, it is POST-only, and it carries an origin check. Splitting the same logic into a second service would add a network hop, a second deploy, and a second place for the secret key to live, and would buy nothing at this size.

2The trust boundary

There is exactly one security rule to remember, and the rest of the security design follows from it.

The one rule

Never query Supabase from the browser. If a file starts with 'use client', it must not import anything under lib/supabase/ or lib/repo/.

The secret key — sb_secret_..., or the legacy service_role key it replaces — bypasses every access rule in the database. Both resolve to the same service_role Postgres role, which carries BYPASSRLS. It lives in a server-only environment variable and must never reach a browser. Three independent mechanisms keep it there, so forgetting the rule is caught rather than shipped:

GuardWhereWhat happens if you slip
import 'server-only'Top of lib/supabase/admin.ts, lib/auth.tsThe build fails. A client component importing it cannot compile
Row Level SecurityAll 9 tables, enabled, no permissive policyA leaked anon key reads nothing at all
scripts/check-bundle.tsRuns after every buildScans the emitted client files for the key and fails the build

That third one is why npm run build ends with a line like check-bundle: 55 client files scanned, no secret key found. The file count moves with the build; what matters is the second half. It is a belt on top of two braces, and it costs a second.

The scan looks for the variable name, the sb_secret_ prefix, and — when the build can see the key — the key's own value. That last one is the finding that actually matters, and it only works if the key is in the environment, which is why package.json passes --env-file-if-exists to that script and not only to preflight. Without it the scan says so rather than implying it checked more than it did.

Who may do what

Authorisation is checked on the server on every request, never by hiding a link. lib/guard.ts holds the page guards so the rules cannot drift apart between routes:

3The daily clock

The whole product runs on one repeating 24-hour cycle. Understanding this is most of understanding the system.

Every paper carries its own window

Opening and last-entry are set when a paper is scheduled, and stored on the paper. The admin console's Default times screen holds the times a new paper is offered; changing it never moves anything already scheduled.

That is what allows more than one paper in a day — a morning set and an evening one, say. Two conditions apply:

  • Their windows may not overlap, counting the running time and not just entry. Scheduling refuses an overlap and names the paper it clashes with.
  • A student may have only one counted attempt open at a time, enforced by a database index. Two papers open at once would otherwise mean splitting one attempt’s minutes across two clocks.

The hard stop is not stored. It is always entry close plus one paper, so the guarantee that the last entrant gets a full attempt holds whatever times you pick. That has one consequence worth knowing:

Entry cannot close later than 11:15 PM

Because 11:15 plus a 45-minute paper is exactly midnight — and a longer paper has to close entry earlier still. Any later and the attempt finishes on the next calendar day, where it would sit on the wrong date for the archive, the leaderboard and the sweep — all of which key off the paper's own date. The form refuses it, and so does a database constraint, so the rule cannot be worked around by writing to the table directly.

Everything else is free. A morning slot of 6:00 to 7:30 works exactly as well as an evening one, and every surface that prints a time reads it from the paper: the home page countdown, the dashboard, the briefing, the admin console.

Nothing keys off the calendar day any more

Three rules used to wait for midnight. They waited for the paper's own hard stop next. They now wait for the reader — each step moving the unlock closer to the person it is actually for:

RuleTo youTo everybody
Answers and solutionsWhen you hand the paper inAt the hard stop, sat or not (FR-6.3.2)
Your rank, and the boardWhen the attempt is scoredImmediately — the board is one board, and it moves through the day
The paper in your archiveWhen you hand it inAt the hard stop

The gate is the same in all three: a finished attempt of your own, or the paper having closed. So a paper sat at breakfast is reviewable at breakfast, and nothing about it is ever shown to somebody who could still take it.

Why almost nothing is scheduled

A job that must fire the moment a paper opens for the product to work is a job that will one day not fire. Instead, lib/time.ts answers “is this paper open right now?” from the current time every time a page loads. India has never observed daylight saving, so IST is a fixed UTC+05:30 and all of it is plain arithmetic with one offset.

The tail between last entry and the hard stop is one whole paper, and it is not slack. A student starting one minute before entry closes still gets every minute the paper allows; the hard stop is defined as exactly that. Nobody ever sits a shortened paper.

One job does run, and it is called the sweep throughout this document: twice a day it closes and scores every attempt still open past its hard stop. Nothing waits on it. Opening a finished paper scores it too, and the admin console has a button for the same run, so a sweep that is late or missed costs nothing. It used to be called the nightly job, from when papers only ran at night.

What the clock no longer decides

One reversal is worth stating before the rest of this section, because it undoes an assumption the earlier drafts leaned on. A paper settles per student, not per clock. The result, the answers, the rank, the comparison and the board all arrive when an attempt is scored — not at the paper's hard stop.

The gate that replaced the clock is the viewer's own finished attempt. That keeps the property that actually matters: nothing about a paper is ever shown to somebody who can still sit it. What it gives up is that a student who has finished could pass the answers to one who has not — a deliberate trade, argued in the PRD under FR-4.2. Three consequences fall out of it:

  • The board is live and the same for everybody. loadCounted counts every finished attempt on every scheduled paper; it no longer filters by close. A paper joins the board when the first student finishes it, or at its close if nobody did.
  • Streaks still wait. They are measured over papers that have closed (streakKeys), because on a live paper the first hand-in would put it on the board and break the streak of everyone who has not sat it yet — which would then heal an hour later. A streak is about the day, so it waits for the day's paper to settle.
  • Every provisional figure says so. While entry is open a rank is “2nd of 3 so far”, not “2nd of 3”. A number that will move is never dressed up as final.

The one time the clock is overruled

There is a single exception to “everything is derived”, and it is deliberate: tests.ended_at. An admin can end a paper for everybody, on the spot, whatever its window says — because the alternative, when something has gone wrong at ten past ten, is watching a broken paper run until midnight.

The stamp beats every other time on the paper. From that instant windowState reports CLOSED, nobody new can start, the hard stop moves to the stamp so an attempt still running has run out of time, and answers, the archive and the leaderboard all open. Two properties keep it honest:

  • It can only ever bring the stop forward. hardStopAt takes the earlier of the stamp and the derived stop, so a stale row or a skewed clock can shorten a paper but never extend one past the day its constraint keeps it inside.
  • Ending is a write, not just a flag. Setting the stamp is the first half; the second is the ordinary overdue sweep, run for that paper alone, which submits and scores every attempt still open. The sweep does not decide to cut anybody short — by the time it runs, the paper already has.

Because it is stored rather than derived, every read of a paper has to carry it. PAPER_WINDOW_COLUMNS exists for that, and paperWindowOf throws on a row that lacks the column rather than defaulting it: absent reads exactly like “never ended”, which would silently turn an ended paper back into a running one for whichever screen forgot.

The boundaries are pinned by tests, so a mistake surfaces as a red test rather than a locked-out student.

Rules the database will not let you break

Three of the rules that make more than one paper a day safe are indexes and constraints, not application checks — so they hold even against a hand-written update in the SQL editor.

ConstraintOnWhat it prevents
tests_one_scheduled_per_date_and_openingtestsTwo scheduled papers opening at the same minute of the same day. Partial on status = 'SCHEDULED', so drafts for one day may sit side by side while you prepare them.
attempts_one_live_per_userattemptsA student sitting two counted papers at once, which would split one attempt across two clocks. Partial, so an admin's dry run never blocks anyone.
tests_window_within_the_daytestsEntry closing so late that the last entrant's attempt spills past midnight, onto a date the archive and the board do not key on. Compares against attempt_sec, so a longer paper needs an earlier close.

Two triggers that say no, and one that keeps up

A paper with real attempts against it cannot be deleted, and cannot be moved back to draft. Both are enforced by database triggers rather than UI checks, because the consequence — scores pointing at questions that no longer exist — is unrecoverable.

The third, sync_attempt_sec, keeps tests.attempt_sec equal to the sum of the paper's sections through every insert, duration change, move and delete. It is a trigger rather than a line in save_paper because save_paper being the only writer is true today, not a guarantee — and a length that silently disagrees with the sections it summarises shows up as a student losing time.

6Taking a paper

The test engine is the one screen where being wrong is expensive, so almost nothing about it is trusted to the browser.

The clock belongs to the server

The browser shows a countdown, but it never decides anything. Every response write returns the authoritative time remaining, and a section that has run out refuses writes regardless of what the client believes. Changing the system clock on the laptop does nothing.

Expired sections are closed on read, not by a timer. Somebody who shuts the laptop mid-paper and comes back twenty minutes later lands in the right section with the right time left, and the sections they slept through are recorded as TIMER_EXPIRED rather than quietly reopened.

Not reached versus skipped

These look the same on a scoresheet and mean opposite things, so the engine separates them at the moment they happen.

The answer key never reaches the browser

This is enforced by what the query selects, not by what the UI chooses to render. loadLiveSection reads id, number, text and options — correct_option and solution are simply never in the statement. The card component types the answer as optional and refuses to reveal without one, so the live path has nothing to leak even by accident.

Full screen, honestly

Every browser guarantees a user can leave full screen with Escape, and no web page can override that. Preppy treats it as deterrence and a record, not prevention, and the briefing says so before the student starts:

  • Leaving full screen covers the question with an opaque overlay until they return.
  • The section timer keeps running throughout — otherwise leaving would be a pause button.
  • Two counters increment, and appear on the result page and in the admin attempts table.
  • It never ends the test, at any count.

The pattern

Four sections, in this order. A fifth section, or the right four out of order, is a blocking error — the sections and their order are the exam's, not a setting.

The numbers, though, are configurable. Every one of them comes from one of two places:

Put tables in table, never in text

A table drawn with aligned spaces loses its columns when rendered in a browser. As structured headers and rows it displays correctly, stays searchable, and cannot be the wrong file.

Only these fields

Every object takes exactly the fields listed above and nothing else. An unknown key is a blocking error, not ignored — a misspelling such as "direction" for "directions" would otherwise drop a whole passage without a word. The message suggests the field you probably meant.

Images

For a DI chart, a puzzle diagram, or a figure a question needs. List the file names in images on the question or the directions block, then choose the files in the Images box on the upload page, next to the paper.

  • Plain names only: letters, digits, ., -, _, ending in .png, .jpg, .webp or .gif. di-chart-1.png works; DI chart (1).png does not.
  • Under 2 MB each, and 10 MB for the paper and all its images together.
  • Every name the paper lists must be uploaded, or it will not publish. To check locally: npm run check -- paper.json --images <folder>
  • Students can load an image only once its paper has opened.

Plain JSON only

The file is parsed strictly, exactly as written. Nothing is repaired, so:

  • Straight quotes only. “ and ” are not JSON, and a word processor's autocorrect inserts them. Write the file in a code editor.
  • No trailing commas after the last item in an object or array.
  • No comments.

A parse error names the line and column, so it is quick to find.

Why JSON and not a PDF

An earlier version read papers out of PDFs, which meant extracting a text layer and then repairing what a word processor does to JSON: curly quotes, long values wrapped across lines, page furniture, a Unicode minus in −0.25. It worked, and it was a permanent source of doubt about whether a question had survived the trip. A .json file has none of those failure modes. If it parses, it is exactly what you wrote.

What blocks publication

Wrong question count in a section · sections missing, repeated, extra or out of order · a number outside its section's band · a gap or duplicate in the numbering · a missing answer, or one naming an option that does not exist · options not contiguous from A · question text under 10 characters · a directions range covering questions that are not there, or overlapping another · a table with no headers, or a row whose width does not match them · an empty difficulty · an unknown field anywhere · placeholder text left over from template.json · an image referenced but not uploaded · a date that is not a real day, or that already has a scheduled paper · sections adding up to longer than a paper may run · marks with more than two decimal places, which the column cannot keep · JSON that cannot be read at all.

Why a numbering gap is an error, not a warning

If Q29 vanishes between Q28 and Q30, it almost never means a number was skipped on purpose. It means a question was deleted by accident. Warning about it would let a 54-question paper go live.

What is only a warning

No solution · no tag · no difficulty · fewer than five options · a very long option · a date that has already passed, since you pick the day and the window again when you schedule it. These publish fine.

Habits that avoid trouble

  • Start from sample.json; the numbering is already correct.
  • Point your editor at schema.json and it catches mistakes as you type.
  • Edit in a code editor, not a word processor.
  • Run npm run check before publishing. It reads the paper exactly the way the site will.

8Scoring and the board

Marking

Marking is set per section, so it is configurable per paper. The shipped default is +1 correct, −0.25 wrong, 0 unattempted, which on the shipped pattern gives a maximum of +55.00 and a minimum of −13.75 — both derived from the pattern rather than written down, so they move with it. Both bounds are pinned by tests, along with a mixed attempt checked for floating-point drift, because a scoring bug is the one defect that corrupts the leaderboard silently rather than announcing itself.

The board is computed on read

There is no stored leaderboard. Ranking runs over the attempts table whenever somebody opens the page. Five students across a few hundred papers is a trivial aggregate, and a snapshot table would need its own invalidation story every time a paper was rescored.

That choice pays for itself in one place especially: correcting an answer key needs no cache invalidation at all. Rescore the attempts and the board is right on the next page load.

RuleDetail
RankingTotal score inside the window on show — the last seven papers by default. Dry runs excluded, which excludes the admin by construction
Tie-breaks, in orderHigher total, then higher average, then higher accuracy, then the higher best single paper. All four inside the window, so “best” on the default board is the best of the last seven. The table's columns are in this order, so reading it left to right is reading the rule
What a total is out ofThe Total header carries it — “Total of 165” — summed from the perfect score of each paper in the window. getLeaderboard returns it beside the rows, because only the query knows which papers the window covers
TiesRows equal on all four share a rank. Less time taken and an earlier first attempt still order them, so the table cannot shuffle between reloads, but neither ranks
StreaksConsecutive papers sat. Skipping one that ran breaks the run, including the morning paper on a day you sat the evening one. Which papers count is per student, like everything else: every paper that has closed, plus one still open that you have already sat — one still open that you have not sat is not in your run at all, or the first student to finish would break everybody else's streak and heal it an hour later. Measured over every paper ever, not just the window on show, or inside “Last 7” a streak would be capped at seven
WindowsLast 7 (default), last 30, all time — counted in papers on the system, not days and not papers you sat, so on a two-paper day “Last 7” spans three and a half days, and somebody who missed all seven is not on the default board at all
A new memberStarts at zero, and the default window is already the one that stays meaningful for them: a board that never resets otherwise becomes a record of who joined first

Why a paper is keyed 2026-11-01#1320

A date used to identify a paper. Now that a day can hold several, the board keys on YYYY-MM-DD#MMMM — the date, then the minute it opens, zero-padded. It stays sortable as plain text, so “the most recent paper” is still just the largest key, and the streak reads the date half back off it.

A cap that would have bitten quietly

PostgREST returns at most 1,000 rows, and a capped response looks exactly like a complete one. Read in a single request, the board would silently start losing attempts once the history grew past that. lib/repo/select-all.ts pages through every result and advances by what actually came back, so a server configured with a lower cap still reads everything.

Correcting a key after the fact

A wrong key with no way back destroys trust in the leaderboard permanently, and the leaderboard is the whole product. So the admin can change a key on a paper that has already run; every attempt is rescored, the paper's key_version increments, and affected students see a note on their result explaining why their score moved. Any question answered correctly by under 10% of the people who tried it is flagged, because that is usually a wrong key rather than a hard question.

What is deliberately not collected

No email address, no phone number, no address. A username maps to a synthetic internal address that never receives mail, which is why there is no password-reset email and the admin is the recovery path.

Integrity recording is two integers per attempt. There is no event log, no timestamps, and therefore no retention policy anywhere in this system. The trade is explicit: the counters tell you that something happened, never when or for how long. For six people who know each other, deterrence was the goal rather than evidence.

11The look

There is a design system, and it is worth knowing its shape before changing anything visual, because most of what it does happens without a call site mentioning it.

Two layers of colour

Nothing in the app names a colour directly. There are raw scales that never change, and semantic tokens that do:

LayerLives inExampleChanges with the theme?
Raw scale@theme in app/globals.css--color-brand-700No. One violet, forever
Semantic token:root, redefined per theme--surface, --text, --line, --accentYes. This is what dark mode is

Components use the semantic layer — bg-surface, text-ink-soft, border-line — so a page works in both themes without a single dark: variant. That is the whole reason dark mode could be added by sweeping 140 class names rather than rewriting eighteen pages.

The rule that keeps it working

Never write a literal colour, and never use one that only exists in light: bg-white, border-black/10, text-[#333]. Each of those is a light card on a dark page, and it will look fine to whoever wrote it. Every token is declared on bare :root first and redefined afterwards, for the same reason — a colour defined only inside a media query never applies to the people who never touched a theme setting, which is most of them.

One frame, every screen

Every page used to choose its own width: 672 px on the result page, 1024 px in the student shell, 1152 px in the admin. The app changed shape as you moved through it, and on a laptop most of the screen was margin.

There is now one shell utility, and it is the viewport minus gutters that grow with it — 16 px on a phone, 44 px on a desktop, capped only past 1920 px. Every header, page and footer uses it, which is also what makes them line up with each other.

UtilityWhat it is for

Width is not the same as using the width

Stretching a 672 px column to 1900 px makes a page worse, not better: one line of content per screenful. The pages that gained the most room were given something to do with it instead — the result page puts the score beside the things you read once and gives the nine-column section table the full width; the briefing reads as two columns; the review page spends the width on a filter rail that stays put while you scroll, and keeps the questions themselves at a measure, because reading a paper is a reading task.

The console is dense on purpose

The admin console and the student app are not the same kind of surface. A student opens four screens a night and the chrome orients them; an admin lives in six, and every band of decoration is something between them and the table they came for. So the console follows what the dense-dashboard world settled on: a rail down the left, quiet chrome, hierarchy from type weight rather than from borders and shadow, and colour kept for state.

What it replaced: the home page was a full-screen decorative panel, two figures, and all six sections repeated as large tiles with a sentence each — the rail’s own list, said twice, taking a screen to do it. It is now four counts sharing hairlines, today’s papers as rows, and the one job an admin runs by hand. The window and pattern screens each stated their current setting in a dark panel; both are the same figures strip now. Inner pages take PageHeader compact and drop their back link, because the rail already says where you are.

The dark theme is lit, not dimmed

This was built twice, and the first attempt is worth keeping on the record because the reasoning was sound and the result was wrong.

Material’s dark-theme guidance is specific: the recommended surface is #121212, a dark grey and deliberately not black, because grey can carry elevation and shadow where black flattens both, and a branded dark surface is that base with a colour laid over it at a low opacity. That advice is right for a neutral product. Applied here it desaturated the brand out of every surface and left a room of brown-greys: a card lifted 1.08 off the page and a border 1.24 off the card. Nothing had an edge. The whole app read as switched off, which is not the same thing as dark.

The landing page never had that problem, because it was the one screen that had kept the brand violet in its own ground rather than tinting it away. Its palette is now the app’s, pushed a little further apart than a landing page needs.

A fill colour is not a text colour

This is the one rule in the system that is not obvious, and breaking it is invisible to whoever does it.

A status colour bright enough to fill a shape is too light to read as words on a pale background. Amber on white is the clearest case: --warn is a good fill and a 2.84:1 text colour, where the standard for body text is 4.5:1. So each status colour comes as a pair:

Measure against the ground the thing actually sits on

The exam header and the landing page are the same deep violet in both themes, so anything sitting on them takes fixed colours, never semantic tokens. The section timer is the example worth remembering: it used --bad, which lightens in dark mode, and that put white text on a light red at 3.48:1 — on the one number a student is watching. The energy colour

--zap is a hot pink sitting next to the brand violet on the wheel, so it reads as heat rather than as a second brand. It carries streaks, ranks, a personal best, and the one button a screen exists for (btn-zap) — the moments the product exists for. Buttons have a lip

Every btn carries a hard offset in its own darker shade (--lip, 4px), and on press the face travels the full height of it and the lip goes with it. One pixel of travel reads as a hover; four reads as a press, which is most of the difference between a form and a game. The lip survives prefers-reduced-motion — it is depth, not motion — but the travel does not.

The theme switch, and its two states

Light or dark. There is no third “system” position, and the stylesheet has no un-stamped case to handle: an inline script in app/layout.tsx always writes data-theme on <html> before the first paint.

StateOn the root elementWhere it comes from
Lightdata-theme="light"The bare :root palette
Darkdata-theme="dark":root[data-theme="dark"], which redefines the same tokens

The operating system still picks the first impression: with nothing in localStorage, the script reads prefers-color-scheme once to choose a starting value. It stops mattering the moment anyone touches the switch, which is what people actually expect a theme control to do. The stored key is preppy-theme, and it only ever holds one of the two words.

Why there is a script in the <head>

Four lines, and they are the only inline JavaScript in the app. Without them a student who chose dark gets one white frame on every navigation, because the server has no way to know what is in their browser's storage. The try/catch falls back to light, which is also what a browser with JavaScript disabled gets from the bare :root palette.

The button itself renders an empty square until it has mounted, for the same reason in reverse: before mount it cannot know which state is current, and one frame of the wrong icon is worse than one frame of nothing. It reads the stamped attribute rather than storage, so it can never disagree with what is actually on screen.

Every transition is held still for one frame during the swap

Two reasons, and the second is a correctness one. A page-wide cross-fade of every colour at once is a smear rather than a nicety. And more seriously: a background-color that reads a custom property does not reliably re-resolve when only that property changes, while a transition is declared on it — the element keeps the previous theme's colour. It is reproducible: the leaderboard's “you” row sat at the dark --accent-soft three seconds after a flip to light, while its own --accent-soft computed to the light value. Removing the transition fixed it; putting it back broke it again.

ThemeToggle therefore adds .theme-switching to the root, flips the attribute, forces a reflow and drops the class on the next frame. One mechanism, and it covers every button, tab and row at once.

This used to have three states

“Match my computer” was the default, and it worked by writing no attribute, so the CSS carried a third case (:root:not([data-theme="light"]) inside a prefers-color-scheme query) that duplicated every dark token. Two palettes are now two blocks, and the duplicate is gone.

13Two databases, not one

Where you are today

There is one Supabase project, preppy-dev, and no deployment. Everything below describes what to do when you put this in front of students — it is not something you have to act on now, and nothing in the app needs it.

One thing does follow from it, though. With a single database, migrations only ever have to be applied in one place, which is why collapsing the early ones into a single baseline was safe. Once preppy-prod exists, the same files have to be run against both, and then the rule about never editing an applied file starts to carry real weight — production would have run it and your laptop would not, or the other way round.

You asked whether local and production should share a database. They should not. Use two separate Supabase projects.

Why

Local work means doing things you would never do to a live system: deleting a paper to test the delete, resetting everyone's password, re-running the schema, seeding attempts to see what the leaderboard looks like with data in it. If that is the same database the students use, one careless afternoon erases a month of scores.

Supabase's free tier allows two active projects, so this costs nothing.

If you would rather start with one

Before any real student has sat a paper, a single project is defensible and simpler — one set of keys to manage. Split before the first night that counts. After that, every day you wait is more data you cannot afford to lose to a stray delete.

Never point your laptop at production

Not "just to check something". npm run seed -- --reset against production changes every student's password without warning, and the old ones are gone. If you genuinely need to look at live data, use the Supabase dashboard's Table Editor, which is read-first and does not run your code.

  1. Upload a paper. Admin → Upload → choose format/sample.json. It is a complete 55-question paper.
  2. Set its date to today and schedule it.
  3. Dry run it. A dry run ignores the paper's window, so you can take it at any hour. It never counts, and the next one replaces it.

That gives you a filled result page and something in the archive within a few minutes.

How migrations work

If you have not met migrations before

A database does not just appear with the right tables in it. Something has to create them, and later, when the app needs a new column, something has to add that too — without throwing away what is already stored.

A migration is one file of instructions for doing that: "make this table", "add this column", "add this rule". They are numbered, and they are always run in order. A database remembers which ones it has already had, so running them again does nothing.

You will not usually write them. You will run one command after pulling new code, and read what it says.

There are four files, in supabase/migrations/. Nothing else defines the schema.

FileWhat it holds
0001_baseline.sqlThe schema as it was first applied: the tables, the SQL functions, the triggers, and the access rules. This is the file your database already has
0002_since_baseline.sqlEverything added since, in one file: the default window, a window per paper, the default section pattern, and how long each paper runs
0003_managing_a_live_paper.sqlWhat an admin can do to a paper after it has gone out: tests.ended_at for an early end, and the two functions behind replacing its questions and scoring it again
0004_deleting_a_paper_that_was_sat.sqlThe deliberate route past the delete guard, for throwing a broken paper away along with the attempts on it

The first two were once six. The steps between them were collapsed into one, because they had never been applied to any database — there was no history to preserve. That was a one-off tidy-up rather than the normal way of working, and the paragraph below says what happens next time.

The baseline is not special to the runner; it is simply file number one. Each database keeps a schema_migrations table listing the versions it has had. The runner compares that list against the files on disk and applies whatever is missing, in order. Each file runs inside a transaction with its own tracking entry, so a file either lands completely and is recorded, or does not land at all. A failure leaves the database on the last complete version, never half-way through one.

CommandDoes
npm run migrateApplies everything pending
npm run migrate -- --statusLists what has landed and what has not. Changes nothing — safe to run any time
npm run migrate -- --printPrints the SQL instead of running it, for pasting into Supabase

It needs DATABASE_URL in .env.local, from the Connect button at the top of the Supabase project dashboard. Choose the Session pooler — port 5432, username postgres.[REF]. The direct connection is IPv6-only without the paid add-on and will not be reachable from most networks; the transaction pooler on 6543 has no prepared statements, which the runner uses. Section 14 lays the three out side by side.

Without DATABASE_URL the runner does not fail — it prints the SQL to paste into the Supabase SQL editor, each block ending with the line that records it.

Why your database says both files are pending

Your schema was first applied by hand, before any of this existed, so no schema_migrations table was ever written and the runner cannot see what is already there. --status will therefore list both files as pending, including the baseline you already have. That is expected and not a sign of trouble.

Run npm run migrate anyway. Every file is written to be safe to run twice — it says "create this table if it does not exist" rather than "create this table" — so the baseline passes straight through without touching anything, gets recorded, and only the genuinely new file changes the database. A test exists purely to prove the whole chain survives that.

After that one run, the list is accurate for good.

Changing the structure later

Write a new file. Never edit one that has already been applied. This is the one rule that matters, and it is worth understanding rather than memorising: your database has recorded that it ran 0002, so it will never run it again. Editing that file changes what a fresh database gets and leaves yours behind, and the two drift apart with nothing to tell you.

So the next change is 0003_something.sql, the one after that is 0004, and the count grows. That is normal and not a sign the files need collapsing again.

supabase/migrations/0003_whatever_it_is.sql
begin;

-- Safe to run twice, like every migration here.
alter table attempts add column if not exists notes text;

commit;

Number it one higher than the last, run npm run migrate, and check the app still works.

There are no "down" migrations — no way to run one backwards. Reversing a schema change correctly is rare, and a rollback file that has never once been executed is a guess about a situation you are not in. To undo something, write the next migration.

  2. Upload and read the preview

    Admin → Upload a paper. Attach the .json, and any images it references in the same box. If validation passes it is saved as a draft — not live.

    There is a name box on that screen. Leave it blank and the paper is called whatever the file calls it, which is what most papers want; type something and that wins instead.     Then read the preview to the bottom. Every question is rendered with the same component a student sees, so what you approve is literally what they get.

    Optional but worth it. The real engine, real timers, never counted, never on the leaderboard, repeatable. The fastest way to notice a question that reads badly under time pressure.

  4. Schedule it

    Press Schedule on the preview screen. That is the only place the button exists, so a paper cannot go live without somebody having looked at it. It unlocks at the time you set on the schedule form, on its own date.

Ending a paper cannot be undone

The stamp can be cleared, but the attempts it submitted cannot be un-submitted — a student cut off at question thirty has been cut off. That is why it asks twice and names the number. 17Production setup

A second Supabase project and a Vercel deployment. Twenty minutes, once. Do it in daylight, well before a paper night.

  1. Create preppy-prod

    Exactly as in section 14, steps 2, 3 and 4, but name it preppy-prod:

    • New Supabase project, closest region.
    • Apply the migrations: npm run migrate pointed at the new project, or npm run migrate -- --print and paste into its SQL Editor.
    • Authentication → Email → Confirm email off.

    Check it worked: Table Editor shows ten tables with RLS badges, exactly as dev did.

    Keep its Settings → API Keys page open. You need the project URL and both keys again, and they are different from your dev ones — a key from one project does not work on another.

Never deploy during a paper window

A deploy replaces the running server. Inside a paper's window somebody is probably mid-attempt — their answers are saved, but the interruption is real. Ship outside every window scheduled for that day; the admin home lists them.

Run npm run migrate against preppy-prod before pushing code that depends on it. New code against an old database fails; old code against a new database usually does not.

18Before the first real paper night

One walkthrough, about ten minutes, on production, in daylight. It exercises nearly every query in the system.

Why this specifically

The schema and its functions are tested against real Postgres, and npm run test:live covers every read. What that cannot reach is the writing half — signing in, starting and submitting an attempt, reading an image out of Storage. This walkthrough is how you find out whether any of that is wrong, at a moment when being wrong costs nothing. Run npm run test:live first; it takes five seconds and rules out a whole class of problem before you start clicking.

  1. Log in as admin and change the password

    Proves: Supabase Auth, the synthetic email mapping, the profile read, the must-change-password gate.

  2. Upload format/sample.json

    Proves: the upload path, validation, and save_paper writing a test, four sections, three directions blocks and 55 questions atomically.

  3. Read the preview to the bottom

    Proves: reading a whole paper back out and reassembling it — the reverse of the step above, and the likeliest place a wrong join shows up.

  4. Set its date to yesterday, schedule it, then dry-run it

    Yesterday keeps it out of the way of a real night; a dry run ignores the window so you can still take it. Answer some questions, skip some, leave one whole section untouched, and press Escape once to exit full screen.

    Proves: start_attempt, the response write path, sectional timers, the integrity counters, section advance.

  5. Finish it and read the result

    Proves: finish_attempt and scoring. Check specifically that the section you ignored reads as not reached while the questions you looked at and moved past read as skipped. If those two numbers are the same, something is wrong.

  6. Correct one answer key on that paper

    Proves: apply_rescore. Your score should change and a note should appear explaining why.

  7. Open the leaderboard

    Proves: the read-time aggregation. Your dry run should not appear. If it does, the admin exclusion is broken and that matters before anyone competes.

  8. Delete the test paper

    It has only a dry run against it, so deletion is allowed. Proves the trigger lets go when it should.

If a step fails

The error names the query. Note which step and what it said — that is enough to find it. Nothing here touches a real attempt, so repeat it as often as you like.
