Part I

How it works

The mental model. Read this once and the code stops being surprising.

1The shape of it

Preppy is one Next.js application talking to one Supabase project. There is no separate backend service, no queue, no cache layer, and no second database. Everything is TypeScript.

That is a deliberate size. The system serves six accounts. Every extra moving part would be something that can break at 10 PM while five people wait, in exchange for capacity nobody needs.

What each piece does

PieceJobWhy this one
Next.js 16Pages, server actions, API routes, the cron endpointUI and backend in one project, one language, one deploy
Supabase PostgresEvery piece of durable stateRelational fits the data; transactions make scoring safe
Supabase AuthPassword hashing, sessions, refreshSo no custom crypto is written anywhere in this codebase
Supabase StorageDiagrams for DI sets and puzzlesPrivate bucket; served through an app route that checks permission
VercelHosting and the one nightly cronZero-config for Next; the free tier covers six people

Why no separate backend

A Next.js server action is a backend endpoint: it runs on the server, it is POST-only, and it carries an origin check. Splitting the same logic into a second service would add a network hop, a second deploy, and a second place for the service-role key to live, and would buy nothing at this size.

2The trust boundary

There is exactly one security rule to remember, and the rest of the security design follows from it.

The one rule

Never query Supabase from the browser. If a file starts with 'use client', it must not import anything under lib/supabase/ or lib/repo/.

The service-role key bypasses every access rule in the database. It lives in a server-only environment variable and must never reach a browser. Three independent mechanisms keep it there, so forgetting the rule is caught rather than shipped:

GuardWhereWhat happens if you slip
import 'server-only'Top of lib/supabase/admin.ts, lib/auth.tsThe build fails. A client component importing it cannot compile
Row Level SecurityAll 9 tables, enabled, no permissive policyA leaked anon key reads nothing at all
scripts/check-bundle.tsRuns after every buildScans the emitted client files for the key and fails the build

That third one is why npm run build ends with a line like check-bundle: 27 client files scanned, no service-role key found. It is a belt on top of two braces, and it costs a second.

Who may do what

Authorisation is checked on the server on every request, never by hiding a link. lib/guard.ts holds the page guards so the rules cannot drift apart between routes:

GuardSends you away ifUsed by
requireUser()Not signed in, or you still have an admin-set passwordEvery student page
requireAdmin()The above, or you are not an adminThe whole /admin segment
requireAnySignedIn()Not signed inOnly the change-password page, which must not redirect to itself

3The daily clock

The whole product runs on one repeating 24-hour cycle. Understanding this is most of understanding the system.

Why almost nothing is scheduled

A job that must fire at 10 PM for the product to work is a job that will one day not fire. Instead, lib/time.ts answers “is this paper open right now?” from the current time every time a page loads. India has never observed daylight saving, so IST is a fixed UTC+05:30 and all of it is plain arithmetic with one offset.

The 44-minute tail between last entry and the hard stop is not slack. A student starting at 11:14 PM gets their full 45 minutes, which lands exactly on 11:59. Nobody ever sits a shortened paper.

Changing the times

They live in one object, WINDOW in lib/time.ts. Change them there and the whole system follows — the countdown, the entry check, the hard stop and the briefing text. Twenty-two tests pin the boundaries, so a mistake shows up as a red test rather than a locked-out student.

4Layers

Code is organised so that the parts where a bug is expensive are pure functions with no database access. Those can be tested exhaustively. Everything that touches the network is kept thin enough to read in one sitting.

5The database

Nine tables. Eight hold the product; one holds rate-limit counters.

Four fields carry more weight than their size suggests

FieldOnWhat it buys
is_dry_runattemptsThe entire admin exclusion. Admin attempts are always dry runs, so no query anywhere needs a role check to keep them off the board
was_visitedresponsesThe difference between never reached and skipped. A row is written when a question is opened, not when it is answered
key_versiontests, attemptsOptimistic locking. If an answer key changes while someone is mid-paper, their submission is detected as stale and rescored rather than silently banked against the old key
fullscreen_exits
tab_switches		attemptsAll the integrity recording there is. Two integers, no event log — which is also why this codebase has no log-retention policy anywhere

Work that happens inside the database

Supabase offers no client-side transaction, so anything that must be all-or-nothing is a SQL function called as one round trip:

FunctionWhy it cannot be application code
start_attemptCreates the attempt and opens its first section together. A half-started attempt has no valid state
finish_attemptLocks the row, refuses to double-score, and rejects a submission carrying a stale key_version
save_paperWrites a test, its sections, blocks and 55 questions atomically. A half-written paper would go live with questions missing
apply_rescoreRewrites every affected attempt in one statement and stamps the paper
rate_limit_hitCounting must be shared. A serverless host runs many instances and each would keep its own count
revoke_user_sessionsReaches into auth.sessions, which needs elevated rights

Two triggers that say no

A paper with real attempts against it cannot be deleted, and cannot be moved back to draft. Both are enforced by database triggers rather than UI checks, because the consequence — scores pointing at questions that no longer exist — is unrecoverable.

6Taking a paper

The test engine is the one screen where being wrong is expensive, so almost nothing about it is trusted to the browser.

The clock belongs to the server

The browser shows a countdown, but it never decides anything. Every response write returns the authoritative time remaining, and a section that has run out refuses writes regardless of what the client believes. Changing the system clock on the laptop does nothing.

Expired sections are closed on read, not by a timer. Somebody who shuts the laptop mid-paper and comes back twenty minutes later lands in the right section with the right time left, and the sections they slept through are recorded as TIMER_EXPIRED rather than quietly reopened.

Not reached versus skipped

These look the same on a scoresheet and mean opposite things, so the engine separates them at the moment they happen.

The answer key never reaches the browser

This is enforced by what the query selects, not by what the UI chooses to render. loadLiveSection reads id, number, text and options — correct_option and solution are simply never in the statement. The card component types the answer as optional and refuses to reveal without one, so the live path has nothing to leak even by accident.

Full screen, honestly

Every browser guarantees a user can leave full screen with Escape, and no web page can override that. Preppy treats it as deterrence and a record, not prevention, and the briefing says so before the student starts:

  • Leaving full screen covers the question with an opaque overlay until they return.
  • The section timer keeps running throughout — otherwise leaving would be a pause button.
  • Two counters increment, and appear on the result page and in the admin attempts table.
  • It never ends the test, at any count.

7Publishing a paper

A paper is one JSON file, uploaded with its images in the same request. The format is fixed and documented in format/README.md, with a fill-in template and a complete worked paper beside it.

Why JSON and not a PDF

An earlier version read papers out of PDFs, which meant extracting a text layer and then repairing what a word processor does to JSON: curly quotes from autocorrect, long values wrapped across lines, page furniture, a Unicode minus in −0.25. It worked, and it was a permanent source of doubt about whether a question had survived the trip. A .json file has none of those failure modes. If it parses, it is exactly what you wrote.

What blocks a paper, and what merely warns

Blocks publicationWarns only
Wrong question count in a section · a number outside its section band · a gap or duplicate in the numbering · a missing answer, or one naming an option that does not exist · options not contiguous from A · a directions range covering questions that are not there · a table row the wrong width · an image referenced but not uploaded · a date that already has a paperNo solution · no topic tag · no difficulty · fewer than five options · a very long option

Why a numbering gap is an error, not a warning

If Q29 vanishes between Q28 and Q30, it almost never means a number was skipped on purpose. It means a question was lost while editing. Warning about it would let a 54-question paper go live.

8Scoring and the board

Marking

+1 correct, −0.25 wrong, 0 unattempted. Maximum +55.00, minimum −13.75. Both bounds are pinned by tests, along with a mixed attempt checked for floating-point drift, because a scoring bug is the one defect that corrupts the leaderboard silently rather than announcing itself.

The board is computed on read

There is no stored leaderboard. Ranking runs over the attempts table whenever somebody opens the page. Five students across a few hundred papers is a trivial aggregate, and a snapshot table would need its own invalidation story every time a paper was rescored.

That choice pays for itself in one place especially: correcting an answer key needs no cache invalidation at all. Rescore the attempts and the board is right on the next page load.

RuleDetail
RankingCumulative total score, all time. Dry runs excluded, which excludes the admin by construction
Tie-breaks, in orderHigher total, then higher accuracy, then less time taken, then who started earlier
TiesGenuinely tied rows share a rank
StreaksConsecutive papers attempted, counting back from the most recent. A night with no paper never breaks one
WindowsAll time, last 7, last 30
A new memberStarts at zero. The last-30 view is the one that stays meaningful for them

A cap that would have bitten quietly

PostgREST returns at most 1,000 rows, and a capped response looks exactly like a complete one. Read in a single request, the board would silently start losing attempts once the history grew past that. lib/repo/select-all.ts pages through every result and advances by what actually came back, so a server configured with a lower cap still reads everything.

Correcting a key after the fact

A wrong key with no way back destroys trust in the leaderboard permanently, and the leaderboard is the whole product. So the admin can change a key on a paper that has already run; every attempt is rescored, the paper's key_version increments, and affected students see a note on their result explaining why their score moved. Any question answered correctly by under 10% of the people who tried it is flagged, because that is usually a wrong key rather than a hard question.

9Security and privacy

ConcernHow it is handled
PasswordsHashed and managed by Supabase Auth. No custom crypto exists in this codebase
Database accessServer-side only, service-role key, RLS deny-all as backstop, build-time bundle scan
Answer keysNever selected by any query on the live test path
Paper imagesPrivate bucket. Served through /api/images, which checks who is asking and whether the paper is open
Brute forceRate limits counted in the database, so they hold across serverless instances
Session hygieneStarting a paper signs the account out everywhere else
First loginAn admin-set password must be replaced before anything else is reachable
Write endpointsServer actions, which are POST-only and carry Next's origin check

What is deliberately not collected

No email address, no phone number, no address. A username maps to a synthetic internal address that never receives mail, which is why there is no password-reset email and the admin is the recovery path.

Integrity recording is two integers per attempt. There is no event log, no timestamps, and therefore no retention policy anywhere in this system. The trade is explicit: the counters tell you that something happened, never when or for how long. For six people who know each other, deterrence was the goal rather than evidence.

10Failure modes

What happens when things go wrong, and why it is survivable.

If this happensThen
A student refreshes, or the browser crashesThey resume at the same question with the correct time left. Time that passed is not refunded
Their network dropsA banner appears, answers queue locally and flush on reconnect, the timer keeps running
They close the laptop and never come backThe attempt is scored either by the 12:05 job or the next time anyone opens it, whichever is first
The nightly job does not fireNothing is lost. It is idempotent and re-runnable from a button in the admin console
You publish no paperThe dashboard says so, and nobody's streak breaks
You publish a wrong answer keyCorrect it and rescore. Students are told why their score moved
Supabase is down at 10 PMThe site cannot serve. There is no fallback, and at this size that is the accepted trade
A student changes their computer clockNothing. The server owns the clock
Two people open the same accountStarting a paper signs the other out

The one thing that has never been exercised

Every SQL query typechecks, and 257 tests cover the pure logic around them, but no query has been run against a live Postgres — the machine this was built on had no database to run them against. Section 15 covers the ten-minute check that exercises nearly all of them at once. Do that before a real paper night.

Part II

Running it

Two setups. Local is for changing things and finding out why something broke. Production is the real site. Follow one section at a time; nothing here assumes you write web code.

11The two builds

There are two ways to build this app, and the difference is small and deliberate.

Every command, and when to use it

CommandWhenWhat it does
npm run devdaily While changing thingsStarts a development server that reloads as you edit. Not a build
npm run build:locallocal To reproduce a bugA real production server, built on your machine, with source maps
npm run start:locallocal After the aboveServes that build on port 3000

npm testany Anytime257 tests. Needs no database and takes about a second
npm run typecheckany AnytimeChecks types without building

The short version

npm run dev while you work. npm run build:prod before you ship. The other two exist for the day something behaves differently in production than it did in development, which is exactly when you want a production build you can put a breakpoint in.

12Local setup, once

Do this once on your laptop. It takes about fifteen minutes, most of it waiting for Supabase to finish creating a project.

You need Node 20 or newer and a free Supabase account. Check Node first:

Terminal
node -v
v22.9.0   ← anything v20 or higher is fine

If that says command not found, install Node from nodejs.org — take the version labelled LTS — and open a new terminal window afterwards.

  1. Install the project's dependencies

    In a terminal, from the project folder:

    Terminal
    cd ~/preppy
npm install

    This downloads everything the app needs into a node_modules folder. It is safe to re-run at any time.

  2. Create the Supabase project

    Go to supabase.com and sign in. Press New project.

    • Name it preppy.
    • Choose the region closest to you. If Mumbai (ap-south-1) is offered, take it — every page load makes several database round trips, and distance shows.
    • Set a database password and save it somewhere. You will rarely need it, but it cannot be recovered.

    Provisioning takes a couple of minutes. Wait for it to finish before the next step.

  3. Create the tables

    In the Supabase dashboard, open SQL Editor in the left sidebar, then New query.

    Open supabase/schema.sql from the project folder, copy all of it, paste it into the editor, and press Run.

    You should see Success. No rows returned. That built all nine tables, ten functions, the indexes and the access rules.

    To confirm, open Table Editor. You should see nine tables, each showing an RLS enabled badge. That badge is intentional — it means nothing can read those tables except your server.

    Safe to re-run

    The whole file is written so that running it twice changes nothing. If you are ever unsure whether it applied, run it again.

  4. Copy your keys into .env.local

    In Supabase, go to Settings (the gear), then API. Keep that tab open.

    Back in the terminal:

    Terminal
    cp .env.example .env.local

    Open .env.local in any text editor and fill in three values:

    Line in the fileWhere it comes from
    NEXT_PUBLIC_SUPABASE_URLSettings → API → Project URL
    NEXT_PUBLIC_SUPABASE_ANON_KEYSettings → API → anon public
    SUPABASE_SERVICE_ROLE_KEYSettings → API → service_role

    The service_role key is a master key

    It bypasses every access rule in the database. It belongs only in .env.local, which is already ignored by git. Never paste it into a chat, a browser console, a screenshot, or any file under app/ or components/.

  5. Turn off email confirmation

    Preppy has no email addresses — usernames map to a synthetic internal address that never receives mail. So Supabase must not sit waiting for anyone to confirm one.

    Go to Authentication → Sign In / Providers → Email, turn Confirm email off, and save.

    Skip this and login will fail confusingly

    Accounts get created, but every sign-in is refused as unconfirmed. If login says the password is wrong when you know it is right, come back here first.

  6. Create the six accounts

    Terminal
    npm run seed

  created  admin
  created  student1
  ...

  Passwords are shown once. Copy them now.

  USERNAME    ROLE     PASSWORD
  ---------------------------------------
  admin       admin    quant-rank-4f2a
  student1    student  timer-solve-9b71

    Copy those now. There is no email to send them to and no way to recover them. If you lose one, run npm run seed -- --reset to set fresh passwords.

    Everyone is made to choose their own password the first time they log in; until they do, nothing else in the app is reachable.

  7. Start it

    Terminal
    npm run dev

  ▲ Next.js 16
  - Local:  http://localhost:3000
  Ready in 404ms

    Open localhost:3000. You should see the countdown to 10 PM. Log in as admin, change the password when asked, and you are in.

    Leave this running while you work. To stop it, press Ctrl+C in that terminal.

After editing .env.local, restart

Environment changes are not picked up while the server is running. Stop it with Ctrl+C and start it again. This is the single most common thing to trip on.

13Using it, day to day

Publishing tonight's paper

  1. Write the paper

    Copy format/sample.json and replace the content question by question. The numbering, the section bands, a data table, a puzzle and a passage are all already in place, which makes it a faster starting point than the blank template.

    Check it before you even open the app:

    Terminal
    npm run check my-paper.json

  Quantitative Aptitude    15 q | 12 min | +1/-0.25
  ...
  Publishable

  2. Upload and preview

    In the app: Admin → Upload a paper. You get the validation report and a list of anything the file needed repaired on the way in. If it passes, it is saved as a draft — not live.

    Read the preview. Every question is rendered with the same component a student sees, so what you approve is literally what they get.

  3. Dry run it, optionally

    The Dry run button puts you through the real engine with real timers. It is never counted and never reaches the leaderboard, so take it as often as you like. This is the fastest way to catch a question that reads badly under time pressure.

  4. Schedule it

    Press Schedule on the preview screen. That is the only place the button exists, so a paper cannot go live without somebody having looked at it. It unlocks at 10 PM on its own date.

The rest of the console

ScreenWhat it is for
Admin homeLeads with tonight's status: Scheduled or Not scheduled. Also has the manual run of the nightly job
PapersEverything published or drafted. Open one to preview, correct a key, or dry-run it
AttemptsEvery attempt with score, duration and the two integrity counters. Void one here if you must
PeopleCreate accounts one at a time or paste a CSV. Reset passwords. Deactivate without losing any history
Export question bankDownloads every paper ever published as one JSON file

There is no automated reminder

With no email configured there is nowhere to send one. The admin home tells you tonight's status the moment you open it; for the reminder itself, a recurring 9:45 PM alarm on your phone does the job with no code.

14Production setup

Production is a second, separate Supabase project plus a Vercel deployment. Fifteen minutes, once.

Use a separate Supabase project for production

Do not point the live site at the database you have been experimenting against. You will want to try things locally — delete a paper, reset a password, run the schema again — and none of that should be able to touch a night that counts. Two free projects cost nothing.

  1. Create the production Supabase project

    Exactly as in section 12, steps 2, 3 and 5: new project (call it preppy-prod), run supabase/schema.sql in its SQL editor, and turn Confirm email off.

    Keep its Settings → API page open; you need all three keys again, and they are different from your local ones.

  2. Generate a cron secret

    Terminal
    npm run secret
8f3c9d1e7a4b20c65d8e1f93a70b4c25de6f8a91b3c47d02

    Keep it. It goes into Vercel in the next step, and it is what stops anyone but Vercel Cron from triggering the nightly job.

  3. Put the code on GitHub

    Vercel deploys from a git repository. If the project is not on GitHub yet, create an empty private repository there and push:

    Terminal
    git remote add origin https://github.com/YOU/preppy.git
git push -u origin main

    .env.local is already ignored by git, so your keys do not travel with the code. Check that nothing sensitive is staged before pushing:

    Terminal
    git status --short
(.env.local must not appear in this list)

  4. Import into Vercel

    At vercel.com, sign in with GitHub and press Add New → Project. Pick the repository. Vercel recognises Next.js on its own; leave the build settings alone.

    Before pressing Deploy, open Environment Variables and add four:

    NameValue
    NEXT_PUBLIC_SUPABASE_URLThe production project URL
    NEXT_PUBLIC_SUPABASE_ANON_KEYIts anon public key
    SUPABASE_SERVICE_ROLE_KEYIts service_role key
    CRON_SECRETThe string from step 2

    Then press Deploy. Vercel runs npm run build, which is build:prod — preflight, typecheck, all 257 tests, then the build. If any test fails, the deploy fails and the previous version stays up.

  5. Confirm the nightly job registered

    After the first successful deploy, open Settings → Cron Jobs in Vercel. You should see one entry for /api/cron/finalise scheduled at 35 18 * * *.

    That is 18:35 UTC, which is 00:05 IST. Vercel Cron runs on UTC, so the schedule is written in UTC.

    If CRON_SECRET is missing, the endpoint refuses everyone

    Including Vercel. That is deliberate — better a job that does not run than an open endpoint that writes scores — but it does mean you must set it. The production build refuses to start without it for exactly this reason.

  6. Seed the production accounts

    The seed script talks to whichever database its environment points at, so point it at production for one command. Create a temporary file called .env.prod.local holding the production URL and service-role key, then:

    Terminal
    npx tsx --env-file=.env.prod.local supabase/seed.ts
  created  admin
  created  student1 ... student5

rm .env.prod.local   ← delete it straight away

    Copy the passwords, hand them out, and delete that file. Everyone changes their own password on first login.

Deploying a change, afterwards

Once it is set up, shipping is one command. Run the production build locally first so a failure shows up on your machine rather than in a deploy log:

Terminal
npm run build:prod     ← catches it here if something is wrong
git add -A && git commit -m "what changed"
git push                ← Vercel builds and deploys on its own

Never deploy during a paper window

A deploy replaces the running server. Between 10 PM and midnight somebody is probably mid-paper, and while their answers are saved, the interruption is real. Ship before 9 PM or after midnight.

15Before the first real paper night

One check, about ten minutes, and it exercises nearly every database query in the system at once. Do it on production, in daylight, before anyone is depending on it.

This is the gap worth closing first

Every query in this codebase typechecks, and 257 tests cover the logic around them, but no query has ever run against a live Postgres. This walkthrough is how you find out whether any of them is wrong, at a moment when being wrong costs nothing.

  1. Log in as admin and change the password

    Proves: Supabase Auth, the synthetic email mapping, the profile read, and the must-change-password gate.

  2. Upload format/sample.json

    Proves: the upload path, the repair layer, validation, and save_paper writing a test, four sections, three directions blocks and 55 questions atomically.

  3. Read the preview to the bottom

    Proves: reading a whole paper back out and reassembling it — the reverse of the step above, and the one most likely to reveal a wrong join.

  4. Schedule it for a date in the past, then dry-run it

    Set the date to yesterday so the paper is out of the way of a real night. A dry run ignores the window, so you can still take it. Answer some questions, skip some, deliberately leave a whole section untouched, and press Escape once to leave full screen.

    Proves: start_attempt, the response write path, the sectional timers, the integrity counters, and section advance.

  5. Finish it and read the result

    Proves: finish_attempt, scoring, the section breakdown, and — check this specifically — that the section you ignored shows as not reached while the questions you looked at and moved past show as skipped. If those two are the same number, something is wrong.

  6. Correct one answer key on that paper

    Proves: apply_rescore, and that your score changes and a note appears explaining why.

  7. Open the leaderboard

    Proves: the read-time aggregation. Your dry run should not appear on it. If it does, the admin exclusion is broken and that is worth fixing before anyone competes.

  8. Delete the test paper

    It only has a dry run against it, so deletion is allowed. Proves the trigger lets go when it should.

If something breaks

The error message names the query. Note which step failed and what it said — that is enough to find it. Nothing in this walkthrough touches a real attempt, so you can repeat it as often as you like.

Backups

The database is the question bank — once a paper is published, Postgres is the system of record and the .json file you wrote it in is only a working copy. Supabase takes automatic daily backups on every project, including free ones.

For a copy that does not depend on Supabase still being there, use Export question bank on the admin home. It downloads every paper ever published as one JSON file. Worth doing monthly, and worth doing before anything that touches the schema.
